# Правила работы над LLM Launcher

## Цель

Сохранять простой пользовательский путь: определить оборудование, объяснить подходящие варианты, подготовить проверяемый план, запустить модель, подтвердить её ответ и предоставить управление. CLI и будущий GUI должны использовать общие правила подбора и запуска.

## Структура

- `cmd/llm-launcher`: ввод, вывод, команды и терминальный мастер.
- `internal/domain`: версии схем и общие структуры.
- `internal/hardware`: наблюдения ОС и Docker.
- `internal/catalog`: встроенный каталог и его валидация.
- `internal/recommend`: чистая логика совместимости и подбора.
- `internal/deploy`: Compose, запуск, состояние и API-проверки.

Не переносите правила совместимости в интерфейс и не связывайте сбор инвентаризации с установкой системных компонентов.

## Изменения поведения

1. Сначала сформулируйте проверяемый пользовательский результат и границы поддержки.
2. Изучите текущие типы, фактические команды CLI и тесты. Не меняйте JSON-схему без версии и плана миграции.
3. Для новых возможностей движков используйте первичную документацию и добавляйте ссылку в `docs/SOURCES.md` или рядом с записью каталога.
4. При изменении параметров запуска отдельно укажите добавления, замены и удаления с причинами.
5. Обновите пользовательскую документацию и отчёт о том, что проверено фактически.

## Подбор модели

Сначала проверяйте OS/архитектуру/backend/драйвер/формат, затем память и задачу. Различайте RAM хоста, лимит Docker VM, VRAM каждой карты и неизвестные значения. Не складывайте GPU VRAM, пока не реализованы конкретный режим параллелизма и его проверки.

Ресурсные оценки помечайте как оценки, указывайте контекст и число параллельных последовательностей. Не называйте ранжирование моделей benchmark или оценкой качества. Для длинного контекста добавляйте соответствующий ресурсный расчёт и тест.

Каталог должен содержать точный идентификатор, формат весов, поддерживаемые задачи, лицензию, источник и ограничения. Не назначайте лицензию всем размерам семейства по одному model card. Новая запись каталога не получает статус аппаратно проверенной автоматически.

## Управление Docker

Стартовый профиль публикует API только на loopback и управляет собственным Compose-проектом. Сохраняйте проверки принадлежности, целостности и блокировку управляющей операции. Вызовы системных утилит передавайте как массив аргументов; не собирайте shell-команды из пользовательского ввода.

Удалённый daemon требует инвентаризации целевого сервера, а не местного компьютера. Не включайте remote deployment одним снятием текущей проверки endpoint.

`down` сохраняет веса. Удаление томов, глобальная Docker-очистка, установка драйверов, изменение firewall и перезапуск Docker не входят в обычный запуск модели. Такие функции требуют отдельного явно выбранного пользователем сценария с конкретным описанием результата.

Используйте явные версии образов, затем digest там, где он известен. Не заменяйте их на `latest`. Model tag тоже может меняться; для воспроизводимости нужны зафиксированные веса/revision и сведения об их происхождении.

Не добавляйте `--privileged`, автоматический `--trust-remote-code`, Docker socket внутрь модельного контейнера или публикацию порта на все интерфейсы как универсальное исправление ошибки.

## Проверка готовности

Health endpoint подтверждает только свой контракт. Дополнительно проверьте выбранную модель настоящим текстовым или embedding-запросом. Пустой ответ с HTTP 200 — ошибка smoke test. Для выбранного GPU-режима проверяйте фактическое использование GPU, если движок может незаметно перейти на CPU.

Системные процессы и HTTP-запросы должны иметь таймаут и поддержку отмены. После неудачи не удаляйте пользовательские веса ради «чистого» повторения. Вывод ошибки должен объяснять этап и полезную следующую проверку.

## Проверки изменений

```bash
go test ./...
go vet ./...
bash scripts/build.sh
```

Добавляйте тесты на поведение и риски, а не на буквальное совпадение реализации. Используйте fixtures для низкой памяти, неизвестной VRAM, нескольких GPU, ограниченной Docker RAM и недоступного daemon. Для API используйте локальный тестовый HTTP-сервер с успешными и ошибочными ответами.

После изменений системного сканера проверяйте соответствующую ОС. После обновления движка — реальный контейнер и модель. Отдельно сообщайте «скомпилировано», «проверено на mock», «запущено на CPU», «запущено на GPU». Не выдавайте успешную кросс-компиляцию за проверку на целевом устройстве.

## Диагностика и документация

Не сохраняйте API-токены, Docker credentials, полный environment или тексты пользовательских запросов в диагностический пакет по умолчанию. Инвентаризация может содержать UUID GPU и локальные пути; документируйте это и предоставляйте просмотр.

Перед выпуском согласуйте README, `help`, каталог, примеры, план и фактический отчёт тестирования. В архив не включайте кеши Go, скачанные модели, локальные секреты и временные артефакты тестового запуска.
