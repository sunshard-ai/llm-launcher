# Проверка прототипа

## Что считать доказательством

У проверки четыре отдельных уровня:

| Уровень | Что подтверждает | Чего не подтверждает |
| --- | --- | --- |
| Сборка | Go-код компилируется в нужный формат бинарника | Работа системных probes на целевой ОС |
| Автоматические тесты | Поведение на контролируемых данных, обработку ошибок, API-контракты | Доступность реального драйвера и загрузку весов |
| Реальный CPU-запуск | Docker, сеть, загрузку и ответ модели на конкретном стенде | Работу GPU |
| Реальный GPU-запуск | Работу выбранного сочетания ОС, драйвера, GPU, движка и модели | Все другие GPU, модели и контексты |

`go test` с HTTP-mock или фиктивным Docker-процессом не является запуском vLLM/Ollama. Кросс-компиляция Windows `.exe` не является тестом на Windows.

Результаты проверки конкретной поставки следует читать в отчёте сборки, если он включён в архив. Этот документ задаёт процедуру и критерии; таблицы ниже не заявляют, что все стенды уже пройдены. Аппаратная квалификация первой версии завершается на компьютере пользователя.

## Тест 1. Сканер

Linux x86-64:

```bash
./dist/llm-launcher-linux-amd64 version
./dist/llm-launcher-linux-amd64 doctor
./dist/llm-launcher-linux-amd64 scan --json
```

Windows PowerShell:

```powershell
.\dist\llm-launcher-windows-amd64.exe version
.\dist\llm-launcher-windows-amd64.exe doctor
.\dist\llm-launcher-windows-amd64.exe scan --json
```

Сверьте с ОС: название процессора, логические CPU, RAM, видеокарту и VRAM. На NVIDIA сравните с `nvidia-smi`. Доступная память меньше общей — нормальная ситуация. Неизвестное значение памяти GPU должно остаться неизвестным; его нельзя считать полностью свободной VRAM.

Убедитесь, что найден правильный Docker context и Docker сообщает Linux-контейнеры. Для Windows сравните RAM хоста с выделенной Docker/WSL памятью. Если факты определены неверно, сохраните вывод и остановитесь на планировании до исправления сканера.

## Тест 2. Каталог и объяснение выбора

```bash
./dist/llm-launcher-linux-amd64 catalog
./dist/llm-launcher-linux-amd64 recommend --task chat
./dist/llm-launcher-linux-amd64 recommend --task code --runtime ollama
./dist/llm-launcher-linux-amd64 recommend --task embeddings --cpu
```

Ожидание: список зависит от реальных ресурсов, модели имеют понятные ID, движок и ресурсные пояснения. При нехватке памяти выводится объяснение; большой CPU-профиль или неизвестная GPU не должны автоматически превращаться в подходящий вариант.

## Тест 3. Мастер без загрузки

```bash
./dist/llm-launcher-linux-amd64 wizard --dir ./test-preview --dry-run
```

Пройдите подтверждение оборудования, выбор задачи, движка и модели. Проверьте созданные `plan.json` и `compose.yaml`. По умолчанию ожидаются loopback-адрес, один параллельный запрос, явный tag образа и постоянный том для весов. После этой команды контейнеры ещё не должны быть запущены.

### Демонстрация на примере чужого железа

Для проверки логики подбора включены JSON-снимки:

```bash
./dist/llm-launcher-linux-amd64 recommend \
  --task chat \
  --inventory ./examples/hardware/linux-rtx4080-16gb.json

./dist/llm-launcher-linux-amd64 wizard \
  --dir ./demo-only \
  --inventory ./examples/hardware/cpu-16gb.json \
  --dry-run
```

Такая инвентаризация описывает **демонстрационный стенд**, а не текущий компьютер. План помечается `DEMO_INVENTORY`; запуск по нему запрещён. Для реального теста создайте новый план по фактическому `scan`, без `--inventory`.

## Тест 4. Первый настоящий запуск

Выберите небольшую модель через мастер. Для начала на новой машине разумно проверить Ollama. Если GPU ещё не настроена, можно явно выбрать CPU:

```bash
./dist/llm-launcher-linux-amd64 wizard --dir ./test-cpu --cpu
```

Для обычного выбора с GPU:

```bash
./dist/llm-launcher-linux-amd64 wizard --dir ./test-gpu
```

Или запустите ранее созданный по реальному железу план:

```bash
./dist/llm-launcher-linux-amd64 up --dir ./test-preview --timeout 45m
./dist/llm-launcher-linux-amd64 status --dir ./test-preview
./dist/llm-launcher-linux-amd64 test --dir ./test-preview
```

Большая загрузка может потребовать большего таймаута. Успешным считается запрос к выбранной модели с непустым ответом, а для embedding-модели — с непустым числовым вектором. HTTP 200 у `/health` отдельно недостаточен.

Для GPU проверьте фактическую работу движка. У Ollama это видно в `ollama ps` внутри контейнера или в ответе `/api/ps`; у vLLM — в журнале и загрузке GPU. Наличие GPU в контейнере и использование её моделью — разные проверки. [Документация Ollama](https://docs.ollama.com/faq#how-can-i-tell-if-my-model-was-loaded-onto-the-gpu).

В GPU-плане Ollama launcher дополнительно требует ненулевой `size_vram` у выбранной модели после пробного запроса. Это защищает от незаметного полного перехода на CPU; частичное размещение на CPU/GPU отдельно не исключается.

Простой просмотр текущих моделей Ollama:

```bash
curl --noproxy '*' http://127.0.0.1:11434/api/ps
```

В PowerShell:

```powershell
Invoke-RestMethod http://127.0.0.1:11434/api/ps
```

Если порт другой, подставьте его из вывода launcher. Модель Ollama может выгрузиться из памяти после периода простоя, поэтому измеряйте сразу после `test`.

## Тест 5. Сохранение и повторный запуск

Для выбранного каталога выполните:

```bash
./dist/llm-launcher-linux-amd64 down --dir ./test-preview
./dist/llm-launcher-linux-amd64 up --dir ./test-preview
./dist/llm-launcher-linux-amd64 test --dir ./test-preview
```

Ожидание: останавливается только этот Compose-проект; том с весами остаётся; повторный старт использует сохранённые данные. Проверка реестра при `up` возможна, поэтому сохранение весов не означает, что весь сценарий уже квалифицирован для полностью отключённой сети.

## Тест 6. Ошибки и защита соседних сервисов

Выполняйте эти сценарии на отдельном тестовом проекте:

| Сценарий | Ожидаемое поведение |
| --- | --- |
| Docker отсутствует | `scan` работает, запуск даёт инструкцию подготовки |
| Docker daemon недоступен | Понятная ошибка, нет сообщения «модель готова» |
| Нет Compose v2 | Отказ запуска с диагностикой |
| NVIDIA видна хосту, но не контейнеру | GPU-проверка останавливает запуск |
| Занят выбранный порт | Ошибка без остановки постороннего сервиса |
| Недостаточно свободной RAM/VRAM | Отказ подбора или запуска; указана причина |
| Таймаут скачивания | Нет ложного успеха; логи и скачанные части доступны |
| Пустой ответ API с HTTP 200 | Smoke test завершается ошибкой |
| Ответ другого формата | Smoke test завершается ошибкой |
| Изменён управляемый Compose | Проверка целостности блокирует действие |
| Запущены две управляющие операции | Конкурентная операция не портит состояние |
| Выбран удалённый Docker context | Локальный режим отказывает до развёртывания |
| Снимок `--inventory` выдан за реальный план | Развёртывание запрещено |

Не создавайте искусственный OOM на рабочем сервере с чужими нагрузками. В автоматических тестах нехватка памяти моделируется входными данными; реальный стресс-тест выполняется на выделенном стенде.

## Матрица аппаратной квалификации

| Стенд | Минимальный набор сценариев | Статус первой поставки |
| --- | --- | --- |
| Ubuntu x86-64, CPU, 16 GB RAM | Scan, Ollama small model, test, down/up | Нужен реальный CPU-прогон |
| Ubuntu x86-64, NVIDIA 8 GB | Scan, Docker GPU, малая модель | Нужен реальный GPU-прогон |
| Ubuntu x86-64, NVIDIA 16–24 GB | Ollama и vLLM, свободная/занятая VRAM | Нужен реальный GPU-прогон |
| Windows 11, NVIDIA, WSL2 | `.exe`, Docker Desktop, Ollama | Нужен прогон на Windows |
| WSL2 Linux x86-64, NVIDIA | Linux-бинарник, vLLM | Нужен прогон внутри WSL2 |
| Linux ARM64, CPU | Сканер, Ollama CPU | Нужен прогон на ARM64 |
| macOS Apple Silicon, Docker | Сканер, CPU-режим | Нужен прогон на macOS |
| Linux с несколькими NVIDIA GPU | Выбор одной GPU, чужие процессы остаются | Нужен отдельный стенд |

Указанные объёмы памяти — параметры тестовых стендов, а не минимальные требования всех моделей.

## Автоматические проверки разработчика

```bash
go test ./...
go vet ./...
bash scripts/build.sh
```

При доступной сборке с race detector можно дополнительно выполнить `go test -race ./...`. Такой прогон особенно полезен после изменений блокировок и конкурентного управления, но не заменяет аппаратные тесты.

Хорошие тесты проверяют наблюдаемое поведение: отказ от несовместимого профиля, отсутствие подмены неизвестной памяти, ограничение выбранной GPU, корректность запроса API, обработку пустого ответа, сохранение томов. Не следует заполнять пакет тестами, которые лишь повторяют строковые константы реализации.

## Форма результата полевого теста

```text
Дата и версия launcher:
ОС и архитектура:
Docker / Compose / context:
CPU / RAM доступная / RAM Docker:
GPU / свободная VRAM / драйвер:
Task / runtime / model ID:
Context / port:
Сканер определил оборудование правильно: да/нет
Время первого скачивания и старта:
Результат test:
Фактическое использование GPU:
Результат down/up:
Ошибка и последние строки logs, если есть:
```

Снимок `scan --json` и этот короткий протокол достаточны для следующей итерации правил подбора. Не отправляйте токены реестров и полный Docker config.

## Полевой тест Windows EXE и Linux/NVIDIA

1. На Windows x64 с Docker Desktop в режиме WSL2 откройте `dist/LLM-Launcher-Windows-x64.exe`. Проверьте иконку в Проводнике и отсутствие дополнительных окон консоли.
2. Выберите папку с пробелами или кириллицей в пути, задачу «Чат и тексты», одну GPU и небольшой профиль. Проверьте GPU, контекст, локальный порт и том весов в Compose перед запуском.
3. Запустите план. Дождитесь результата теста API. Во вкладке управления проверьте статус, логи, остановку и повторный запуск с сохранёнными весами. Повторите с архивированием и восстановлением. В другой пробе отмените запуск на этапе загрузки и проверьте `status` перед повторным запуском.
4. На Linux x86-64 с NVIDIA Container Toolkit запустите тот же цикл из CLI. Сначала Ollama на одной GPU, затем отдельно vLLM на одной GPU. Запишите версии ОС, Docker, драйвера, модель карты, доступную VRAM, модель, контекст и результат запроса.
5. Для будущего multi-GPU профиля нужен Linux-стенд минимум с двумя совместимыми картами. Критерий — API отвечает, фактическое распределение соответствует выбранным UUID, а занятая или пропавшая карта даёт отказ до запуска.

## Проверка 0.2.0 на стенде с NVIDIA

1. Откройте EXE и выберите модель Ollama. В «Проф. настройках» задайте температуру `0`, максимум токенов `64` и `OLLAMA_KEEP_ALIVE=8m`. Подготовьте план, проверьте краткую сводку и отдельно «Посмотреть детали…». После запуска проверьте имя модели с суффиксом `:configured` и выполните запрос с этим именем.
2. Выберите «vLLM / NVIDIA (эксп.)» и небольшую модель каталога. Назначьте отдельный порт. Сохраните диагностику, результат контейнерного GPU probe и теста API. Проверка не требует удаления уже скачанных весов.
3. Для импорта выберите «Свой HF…» в vLLM или режим llama.cpp. Проверьте опубликованные commit и размер, затем загрузку и повторный запуск. Для закрытого репозитория используйте токен чтения с доступом и убедитесь, что он отсутствует в файлах плана и свойствах контейнера. Протокол тестирования не должен содержать токен.
